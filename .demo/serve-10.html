SERVE-10: nothing leaves the machine

The last check that needs your eyes. This page explains what the requirement actually claims, what is already proven mechanically, what is left for you specifically, and the exact four steps — so the check takes a minute rather than an investigation.

01 — THE CLAIMWhat the requirement says

"Neither the artifact nor the chrome makes an outbound network request; no CDN assets are ever injected."

Two separate promises, and they fail in different ways. The first is about the served session: while illuminate is running, every byte the browser asks for comes from the local daemon. The second is about the exported file: once illuminate is gone and you open the artifact from disk, it still renders completely, because nothing in it points anywhere.

This matters because the whole product is pointed at private repositories. A single webfont or analytics beacon means the paths, filenames and prose of your source have been handed to somebody's log. There is no partial credit here.

02 — ALREADY PROVENWhat you do not need to re-check

e2e/export-standalone.spec.ts — the zero-request export proof

A real Chromium opens the exported file over file:// with the daemon stopped, and every request the page makes is counted. This is the exported half of the claim, run on every browser suite.

test/export/no-remote-refs.test.ts — the source-wide backstop

Counting requests at runtime only catches what a given page happened to reach for. This test works from the other end: it scans a real export for any remote reference that survived without a warning. A reference that never fires on the page you tested is still a reference.

src/chrome/chrome-css.ts — the shell stylesheet

The chrome is the newest surface and therefore the likeliest place for a CDN font to have crept in. It is a plain string constant with no @import and no url(https://); its own header comment states the rule, which is a weaker guarantee than a test but a real one.

03 — MEASURED JUST NOWBoth halves, on this build

Rather than ask you to confirm something unmeasured, both paths were driven and every request counted first — including requests that fail or are aborted, which a Network tab shows but a naive listener misses.

So the expected result of your check is already known. That is deliberate: a check whose outcome is a surprise is a check you have to debug, and this one should take a minute.

04 — WHAT YOUR EYES ADDWhy this is still open

src/daemon/server.ts — the shell document

Every automated check above looks for something it already knows to look for. The shell is hand-written HTML with an inlined stylesheet and one local script tag — and a request nobody thought to assert against is exactly the kind a test cannot fail on. DevTools shows you everything the page asked for, including the thing the suite has no assertion for. That is the entire difference between this check and the green suite.

05 — THE CHECKFour steps

  1. Open the served session and press F12 → Network. Tick Disable cache, then reload.
  2. Exercise it. Hover a few anchored blocks, click one and pick an intent, Tab to another and press Enter, open and Escape the picker, write a note and queue it, and click through the Review / Findings / Agent tabs in the rail.
  3. Sort by Domain. One glance is the whole check: every row should read 127.0.0.1. Any other domain is a fail, however harmless it looks.
  4. Then the exported half. Run illuminate export <file>, stop the daemon, and open the exported file directly from disk. It should render completely, with the Network tab showing only the file itself.

One correction to the old steps

VALIDATION.md said "open the findings drawer"

That drawer no longer exists — the review rail owns findings now, as a tab. The step above is the current equivalent. Worth knowing before you go looking for a control that was removed.
